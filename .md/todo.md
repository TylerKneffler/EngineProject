## High-FPS rendering research and implementation plan

- [ ] **Profile CPU, vertex, pixel, bandwidth, and shadow costs before choosing a technique.** Establish repeatable camera routes and target frame budgets at the intended output resolutions. Capture per-stage GPU timings and valid pipeline counters for terrain, bark, leaves, shadows, and post-processing; report average, median, and tail values with GPU/driver/API/build provenance. Include cold/warm scene load, memory use, and quality captures so optimizations address measured bottlenecks rather than triangle counts alone.
- [ ] **Reduce foliage masked-pixel overdraw and material cost.** Measure leaf coverage/overdraw and shader cost by LOD with an overdraw view and pipeline counters. Prototype more compact leaf cards, tighter alpha bounds, mip-aware alpha coverage, alpha-tested depth prepass only where it reduces repeated shading, and simpler far-LOD foliage shading. Compare foliage-specific mip/filter/material variants at fixed exposure and lighting; preserve density, silhouette, translucency/lighting response, and avoid replacing geometry cost with larger fragment cost.
  Validated DX12 baseline (2026-11-09): matched 1920x1080 oak Play capture with `ENGINE_GPU_WORKLOAD_COUNTERS=1`, 40 valid Play samples, unchanged input provenance. Median total GPU stage time 13.42 ms; leaves 8.32 ms (p95 10.74), bark 1.99 ms, shadows 1.79 ms, terrain 0.20 ms. Leaves generated 32.58M pixel-shader invocations and 1.56M input primitives per Play frame; 177 physical draws, ~15.2K submitted instances and ~31.3M submitted triangles. This confirms foliage leaves are the top measured GPU stage, but counters alone do not distinguish overdraw from shader/material cost. Capture and raw stage profile: `.local/performance-logs/oak-workload-counters-20261109.jsonl` and `.local/performance-logs/oak-workload-counters-20261109-stages.log`; provenance `.inputs.json`. Next isolate overdraw/material cost by LOD using matched views and a dedicated overdraw/alpha experiment, then test compact cards, tighter alpha bounds, mip-aware coverage and far-LOD shading.
  Controlled DX12 shader audit (2026-11-09): at 1920x1080, the alpha-mask diagnostic retained about 36.86M leaf pixel-shader invocations but took 1.79 ms; the full foliage shader took 6.04 ms at about 36.77M invocations. Pixel coverage is therefore not the only major cost; full material/light/shadow work adds substantial GPU time. An alpha-tested depth prepass doubled vertex invocations and was resolution-sensitive: it improved the isolated leaf stage at 1920 but regressed it at 960, so do not enable it globally. Mip-bias +4 and the existing “material-cheap” audit candidate did not yield a repeatable improvement in the captured run and need visual review/repeated timing before adoption. Audit files: `.local/foliage-alpha-audit-20261109/` and `.local/foliage-material-audit-20261109/`.
  Code-path finding: `textureLod.simplifyShading` had no effect in `PSFoliageMain` (`Engine/Core/Shaders/Object/Object.hlsl`); the material-cheap audit only set this flag, explaining why it was not a valid cheaper-foliage implementation. An opt-in distance-blended shadow approximation now uses that flag for foliage while leaving alpha coverage unchanged. Initial DX12 oak cluster captures at 960x540 (256 m groups; Intel UHD; 32 steady and 8 camera-sweep valid GPU samples per variant) were mixed: steady leaf-stage median was 14.64 ms baseline vs 16.07 ms candidate; camera-sweep median was 16.54 vs 16.16 ms. Camera-sweep leaf pixel-shader invocations were similar (8.55M vs 8.52M), but steady invocation counts differed substantially between runs despite matched geometry, so these short captures do not establish a repeatable gain. Matched DX11 entrance images show a small candidate canopy color shift; DX11 workload counters were unavailable. Keep the option disabled by default and the broader item open: repeat fixed-view DX12 profiling at 1920x1080 with stable workload counters, capture color at near/mid/far regions, then decide whether to tune or reject the approximation. Evidence and limitations: `.local/performance-logs/foliage-shading-dx12/`, `.local/performance-logs/foliage-shading-candidate/`, report `.local/performance-logs/foliage-shading-dx12/report.md`.
- [ ] **Tune the existing screen-size LOD path for trees and meshes.** The engine already has screen-size LOD and hysteresis; enable it as a reversible oak-layer candidate and tune thresholds using projected error instead of relying only on camera distance. Test cross-fade/dither transitions and density-preserving canopy representations. Keep visible LOD selection independent from shadow LOD. - [ ] **Improve instance and cluster culling granularity.** GPU instance culling and indirect draws already exist. Benchmark the current 256 m prefab groups against smaller spatial clusters, preserving conservative per-cluster bounds, coherent LOD/material grouping, and temporal visibility where appropriate. Measure culling overhead, visible instance counts, draw/dispatch counts, GPU vertex and pixel work, and camera-motion popping; avoid coarse groups that submit large off-screen canopy areas.
- [ ] **Prototype distant canopy representations for fill-rate as well as geometry.** Compare the installed impostor with multi-view/octagonal impostors, layered/volumetric impostors, and low-density opaque/alpha-tested canopy proxies. Evaluate projected coverage and overdraw, shadow response, view-angle error, color continuity, mip behavior, and transition quality. Reject representations that reduce triangles but expand shadow-map or camera pixel coverage.
- [ ] **Research a hierarchical leaf-cluster LOD alternative (BroadLeaf-style).** Evaluate replacing whole-tree leaf LOD decisions with hierarchical leaf clusters that can be culled and selected at finer granularity, while retaining the existing tree/trunk representation. Prototype one oak asset and compare visible cluster count, leaf triangles, draw/dispatch overhead, masked-pixel work, canopy silhouette, and transition flicker against the current tree-level LODs. Keep this separate from impostor experiments so its effect is measurable; proceed only if finer culling reduces total frame time without canopy holes or unstable appearance. Reference: [BroadLeaf: Real-Time Cinematic Rendering of Large-Scale Forests (GDC 2023)](https://www.gdcvault.com/play/1028728/BroadLeaf-Real-Time-Cinematic-Rendering).
- [ ] **Assess GPU procedural tree generation as a memory/startup research branch.** Build a small feasibility prototype that generates one procedural oak's branch and leaf geometry on-GPU with continuous LOD, then compare geometry memory, scene-ready time, generation/render GPU cost, wind and shadow support, and image quality against baked prefab LODs. The published GPU work-graph/mesh-node approach reports a specific AMD hardware/API implementation; verify feature availability and viable DX11/DX12/Vulkan paths before any production commitment. Do not treat the paper's demo timings as a forecast for this engine. Reference: [Real-Time GPU Tree Generation (Eurographics/High-Performance Graphics 2025, GPUOpen)](https://gpuopen.com/download/Real-Time_GPU_Tree_Generation.pdf).
- [ ] **Create dedicated low-coverage shadow proxies and budget shadows by scale.** Compare shadow-only proxies (trunk plus sparse canopy/coverage proxy) with current fixed LOD1 and current impostor casters. Investigate cascade-specific LOD, caster culling, shadow distance/fade, update caching, and lower-resolution far-shadow contribution. Record full-refresh and cached shadow cost plus caster vertices/fragments and validate ground contact, coverage, and temporal stability.
- [ ] **Evaluate modern virtualized geometry selectively for foliage.** Prototype cluster-based geometry/meshlet LOD and GPU culling, preserving leaf coverage at distance. Benchmark opaque leaf geometry against masked cards and current LODs on every supported backend. Treat Nanite-style geometry/voxel approaches as a reference or optional backend path: masked foliage may remain fill-rate-bound, and this engine must retain DX11/DX12/Vulkan behavior. Measure memory, streaming/build cost, wind deformation, shadows, and fallback paths before adoption.
- [ ] **Use terrain clipmaps or ring-based terrain LOD for large landscapes.** Compare the current terrain patch/LOD pipeline with nested camera-centered rings and GPU-updated height/normal clipmaps. Measure terrain vertex and pixel cost, streaming/update work, seam quality, and interaction with foliage culling. Adopt only if terrain is a measured bottleneck in the target routes.
- [ ] **Build a cross-backend foliage benchmark matrix.** For each candidate, run deterministic entrance, overlook, dense-canopy, and moving routes at representative output resolutions on DX11, DX12, and Vulkan. Capture CPU preparation, GPU stages, vertices/primitives/fragments, shadow workload, instance counts, memory, screenshots, and quality review. Require repeatable frame-time gains and no visible regression; document unsupported API features and platform-specific fallbacks.
