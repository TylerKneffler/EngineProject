# Engine roadmap

Last updated: 2026-10-26.

Status convention:

- `[x]` Complete
- `[ ]` Incomplete

## Next priorities

### Next terrain FPS and view-distance work

The current 1080p result is from one viewpoint and 9.6 m of walking/running. Prioritize the following work by measured frame cost and visual error, and retain the 25 km camera range and kilometer-scale visibility in comparisons.

- [ ] Extend `.local/tests/TerrainStreamingPerformanceTests.cpp` with repeatable low-ground, ridge-top, and map-edge viewpoints; heading sweeps; human-speed cell/LOD crossings; and cold/warm cache runs. Record p50/p95/p99 frame and GPU stage times, upload stalls, triangles submitted, draws, texture memory, and resident cells. Keep GPU waits outside measured frames. Use [PIX timing captures](https://learn.microsoft.com/en-us/windows/win32/direct3dtools/pix/articles/timing-captures/pix-timing-captures) to attribute any p95 regression before changing the renderer.
- [x] Split the baked far grid into 32-cell mesh tiles with per-tile bounds and frustum culling. A camera-cell crossing updates only affected tiles; the test crossing rebuilt one tile in 0.6 ms and uploaded 294 KiB. Saved sculpt patches and the 22.5 km visible silhouette remain. The 1080p fixed-view run measured 7.3 ms p95, 4.7 ms median GPU time, and 58 peak draws versus 6.3 ms p95, 4.5 ms median GPU time, and 35 peak draws for the former single mesh. The tiles improve update locality but increase draw and scene traversal cost.
- [x] Separate cell-boundary frame cost into manager streaming, far-tile updates, scene rendering, and GPU work. Keep existing terrain batches while an incomplete 4×4 group fills, so arriving cells render individually and the group uploads once when ready. The paced 5 m/s crossing loaded 15 cells in one second with no batch reuploads; fixed-view p95 stayed near 7.0 ms.
- [ ] Reduce cell-arrival render cost without shrinking the 25 km far plane. The paced crossing reached 159 draws at p95 as LOD changes invalidated batches, versus 58 peak draws in the fixed-view run. After the lighting fade, the latest crossing measured 11.7 ms p95; prioritize preserving or promptly rebuilding batches during LOD changes and prefetching the next cell band during human-speed approach.
- [x] Add optional 1080p rendered captures for ground-level range, a high viewpoint, and a cell boundary. Comparing lit, unlit, shadow-disabled, and sun-disabled images identified the dark strip as the 1 km realtime-light cutoff on detailed terrain. One selected directional sun now lights both detailed cells and the distant grid at every view distance; the far grid shades vertices, while detailed terrain samples at most one near shadow texel and fades shadows out by 96 m. The high-view capture checks near and far sunlight.
- [x] Stitch the detailed-to-distant geometry boundary. The first far cell now retains every 4 m height sample along its shared edge and tapers to the coarse grid across one cell; saved far sculpt patches use the same edge heights. A geometry regression checks all 33 samples on each of the four edge directions, and the high-view capture no longer shows the white gaps. The crossing tile upload rose from about 294 KiB to 710 KiB and its rebuild from 0.5 ms to 3.3 ms.
- [ ] Smooth the remaining coarse-to-textured color and normal transition. The far palette uses linear averages of the sRGB material textures, and geometry is stitched, but the boundary still changes texture detail abruptly. Compare filtered near/far normals and add a visual overlap or morph band without duplicate geometry.
- [ ] Replace the single repeated color sample per painted layer with a measured landscape material path: retain normalized paint weights, support optional height-aware transitions from a layer height channel, sample near detail and lower-frequency macro color at distance, and compare stochastic tile variation against the current world-space UV warp. Bind each layer's normal and roughness data as well as albedo where available. Check manual paint across cell borders, texture seams, LOD changes, and the 1080p GPU budget. See [Unreal Landscape layer blending](https://dev.epicgames.com/documentation/en-us/unreal-engine/landscape-materials?application_version=4.27), [distance-based detail texturing](https://dev.epicgames.com/documentation/unreal-engine/adding-detail-textures-to-unreal-engine-materials?lang=en-US), and [NVIDIA texture bombing](https://developer.nvidia.com/gpugems/gpugems/part-iii-materials/chapter-20-texture-bombing).
- [ ] Remove the repeated horizontal color bands in the distant vertex-color grid by baking painted material appearance into streamed, mipmapped far-surface tiles. Match those tiles to the near material blend at the detailed radius; inspect low and high viewpoints after edits and reloads.
- [ ] Bake a filtered height/normal mip hierarchy and select terrain LOD from projected screen error instead of fixed cell radii alone. Add continuous height morphing and crack-free near/far joins; test ridge silhouettes, painted borders, and camera height changes before reducing triangles. Compare the new path against the existing stride 1/2/4/8 cells. See [GPU geometry clipmaps](https://developer.nvidia.com/gpugems/gpugems2/part-i-geometric-complexity/chapter-2-terrain-rendering-using-gpu-based-geometry) and [Landscape LOD](https://dev.epicgames.com/documentation/en-us/unreal-engine/landscape-outdoor-terrain?application_version=4.27).
- [ ] Bake static painted material blends into tiled, mipmapped albedo/normal data for distant terrain, with a fixed texture-memory budget and on-demand page loading. Keep live layer blending in the editor and near game view. Compare far-terrain GPU texture/shader time, memory, and color transitions to the current multi-texture blend. See [runtime virtual texturing](https://dev.epicgames.com/documentation/unreal-engine/runtimevirtual-texturing-quick-start-in-unreal-engine) and [Landscape texture streaming](https://dev.epicgames.com/documentation/unreal-engine/landscape-overview).
- [ ] Test hierarchical terrain visibility using baked per-tile minimum/maximum heights and front-to-back traversal. Cull hills hidden behind nearer ridges without culling a valid skyline from high viewpoints; report rejected tiles and net CPU/GPU time, including cases where culling overhead loses. See [hierarchical terrain visibility](https://research.cs.queensu.ca/home/jstewart/papers/egwr97.html) and [occlusion-query costs](https://developer.nvidia.com/gpugems/gpugems/part-v-performance-and-practicalities/chapter-29-efficient-occlusion-culling).
- [ ] Improve terrain depth cues and recover the fixed-view p95 below 10 ms. The global-sun run measured 12.6 ms p95 at 1080p with 22.5 km visibility; an adjacent sun-disabled run measured 12.0 ms p95, so sunlight alone does not explain the wider frame-time regression. Compare the current single-tap shadow inside 96 m against baked terrain ambient/shadow data and full PBR; add rendered checks for multiple sun angles, material color, and ridge shadow quality. Reprofile far vertex sunlight, near texture blending, and shadow submission on an otherwise idle GPU. Static material shading can be cached as described in [runtime virtual texturing](https://dev.epicgames.com/documentation/unreal-engine/runtimevirtual-texturing-quick-start-in-unreal-engine).
- [ ] Evaluate shared-grid instancing or GPU-driven visible-patch submission only if the expanded benchmark shows CPU draw submission or per-patch culling is material. Compare draw count, CPU render time, GPU time, and implementation cost against existing 4x4 cell batches; do not replace batching on draw count alone. See [Landscape component costs](https://dev.epicgames.com/documentation/en-us/unreal-engine/landscape-technical-guide?application_version=4.27) and [indirect drawing](https://learn.microsoft.com/en-us/windows/win32/direct3d12/indirect-drawing).
